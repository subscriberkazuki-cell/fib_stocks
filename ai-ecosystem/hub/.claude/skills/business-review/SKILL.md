# /business-review — 新規事業の設計と検証

対象: $ARGUMENTS

## 目的
アイデアを増やすことではなく、**実際に成立するビジネスモデル**を作ること。成立しないと分かったら、それも成果として報告する。

## 手順

1. **前提の整理** — 誰の・どんな困りごとを・いくらで解決するのかを1文にする。書けなければそこから詰める
2. **記憶の確認** — Vault の `AI_Hub/01_Projects/Startup/` と `02_Knowledge/Business_Models/` を検索し、過去の案・却下理由を確認する
3. **調査** — `research-analyst` に、市場規模（根拠つき）・既存の競合・海外の類似モデル・価格帯を集めさせる
4. **設計**
   - 収益構造（誰が・何に・いくら・どの頻度で払うか）
   - コスト構造（固定費・変動費・獲得コスト）
   - 単位あたりの採算（1顧客あたり粗利、獲得コストの回収期間）
   - 損益分岐（何件・何人で黒字か）
   - 競争優位（真似されにくい理由。無ければ無いと書く）
   - MVP（最小の検証で何を確かめるか、費用と期間）
   - ロードマップ（検証 → 初期顧客 → 拡大、各段階の判断基準）
5. **Red Team** — `quality-reviewer` に、失敗シナリオ・最も弱い前提・競合の反撃・規制リスクを検証させる
6. **修正と判定** — 指摘を反映し（原則2回まで）、「進める / 条件付き / 見送り」を判断材料つきで示す。最終判断はオーナー
7. **保存** — `AI_Hub/01_Projects/Startup/<案名>/YYYY-MM-DD_review.md`。見送りの場合も理由を `/remember` で失敗知見として残す

## 品質基準
- 数字は前提を明記する（「月額3,000円 × 解約率5%」など）。根拠のない数字は仮定と明記
- 最も弱い前提が1つ特定されていて、それを確かめる最小の方法が書かれている
- 独立レビューの指摘への対応が残っている

## 出力形式

```
# <案名> 事業検証（YYYY-MM-DD）
## 一文で
## 市場と顧客（出典つき）
## 競合・類似モデル
## 収益構造 / コスト構造 / 単位採算 / 損益分岐
## 競争優位
## 最も弱い前提と検証方法
## MVP と ロードマップ
## 失敗シナリオ（Red Team）
## 判定材料（進める / 条件付き / 見送り）
## レビュー記録
```
