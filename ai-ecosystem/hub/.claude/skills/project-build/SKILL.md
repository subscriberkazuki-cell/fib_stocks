# /project-build — 開発ワークフロー

依頼: $ARGUMENTS

## 守ること
- **既存プロジェクトを壊さない。** 作業ブランチを切ってから変更する。未コミットの変更がある場合は、先にオーナーに確認する
- `git push`・デプロイ・本番データベースへの書き込み・ファイル削除は、オーナーの承認なしに行わない
- 実行していないテストを「通った」と書かない
- 売買・送金など実際のお金が動く処理（FRED・BTC BOT）は、**発注を伴うコードを本番設定で動かさない。** テストはペーパー・テストネット・モックで行う

## 手順

1. **調査** — 対象リポジトリの構成、CLAUDE.md・README・テストの走らせ方、直近のコミットを読む
2. **要件定義** — 何ができれば完了か（受け入れ条件）を箇条書きにする。曖昧で実装が大きく変わる点だけ確認する
3. **設計** — 変更するファイルと方針、データ構造の変更、影響範囲、リスクを書く。大きな変更なら、ここでオーナーに見せる
4. **準備** — `git status` を確認し、`git switch -c <作業ブランチ>` を切る
5. **実装** — 小さく区切って実装する。既存のコードの書き方に合わせる
6. **テスト** — 変更した振る舞いのテストを書き、プロジェクトの型チェック・リンター・テストを実行する
7. **独立レビュー** — `technical-qa` に変更点を渡す。実装した本人は判定しない
8. **修正** — 指摘を直して再テストする（原則2回まで）
9. **報告** — 何を変えたか、実行した検査とその結果、残っている問題、次の判断事項（push・デプロイするか）

## 出力形式（最終報告）

```
## 変更内容
## 受け入れ条件と結果（満たした / 満たしていない）
## 実行した検査（コマンドと結果）
## 独立レビューの判定と対応
## 残っている問題・リスク
## オーナーの判断が必要なこと（push / デプロイ / マージ）
```
