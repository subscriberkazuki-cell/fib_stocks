## 2. 予算ガードの位置づけ

課金される外部API呼び出しは、**必ず `BudgetGuard.spend()` の内側で実行する**。

```ts
return this.budget.spend({
  kind: 'business_data',
  provider: 'dataforseo',
  estimatedCostUsd: estimated,
  run: async () => {
    const res = await fetch(...);   // ← 課金される呼び出しはこの中にしか存在しない
    return { value, actualCostUsd: task.cost };
  },
});
```

「呼ぶ前にチェックする」形にしないのは、後からモジュールを追加したときに
チェックを忘れた経路ができるため。呼び出しごと包むことで、
**予算チェック漏れと使用量の記録漏れが同時に防がれる**。

- 超過時は `BudgetExceededError` を投げる（警告表示ではなく停止）
- 月間上限（`MONTHLY_BUDGET_USD`）と1検索あたり上限（`PER_SEARCH_BUDGET_USD`）の2段構え
- 実コストがレスポンスから分かる場合は、見積もりではなく実測を `api_usage` に記録する
- API Route は 402 Payment Required で返し、UIが通常のエラーと区別できるようにしている

## 3. 2段階取得フロー

### Phase 1（`phase1Rules.ts` — AI・Web検索を一切使わない）

取得: 店名 / 業種 / 評価 / レビュー件数 / 座標 / business_id / 電話 / website有無

判定:
1. 営業対象外の組織（公共機関・宗教法人・政治団体）を除外
2. `rating >= minRating` かつ `reviewCount >= minReviewCount`
3. `noWebsiteOnly` なら website フィールドが埋まっているものを除外
   （ただし `includeLowQualitySite` ならリニューアル営業候補として通す）
4. `requirePhone` なら電話がないものを除外

評価を持たないプロバイダ（OSM）では、2 を自動的に無効化する。
そうしないと「評価がnull → 全件落ちる → 0件」になるため。

### Phase 2（`phase2.ts` — Phase 1 通過分のみ）

- **Stage 2**: 「店名 + 市区町村名」でWeb検索して候補URLを収集（`SEARCH_PROVIDER=none` ならスキップ）
- **Stage 3**: 候補URLをドメイン分類（`config/portalDomains.ts`・AI不使用）
  - 独自ドメイン候補が複数あるときだけ、AIに最終判定させる
- **Stage 4**: 公式サイトの品質を実測 → Website Opportunity Score
- 公開ページからメール抽出（推測生成なし・フリーメールは公式サイト掲載時のみ）

Phase 2 完了後、実測値で Lead Score を再計算し、`business_history` にスナップショットを残す。

## 4. 「HPなし」判定と2つのスコア

### Web Presence Score（Webでの露出の弱さ・0〜100）

| 状態 | スコア |
|---|---|
| 公式サイトあり・十分整備 | 0 |
| 公式サイトあり・改善余地大 | 20 |
| SNSのみ | 40 |
| ポータル1件のみ | 50 |
| 複数ポータルのみ | 60 |
| 店舗プロフィールのみ | 80 |
| 独自HPなし＋Web情報も少ない | 100 |

無料ホスティング（Wix無料枠 / Jimdo / `business.site` 等）は独自HPとして数えない。

### Website Opportunity Score（営業機会の大きさ・0〜100）

公式サイトがあっても営業機会があるかを測る**別軸**。20項目を重み付けして
「満たしていない項目の重み合計 ÷ 全体」で算出する。すべて実測値でAI推定は混ぜない。

独自ドメイン / SSL / モバイル対応 / 表示速度 / 情報量 / 店舗写真 / メニュー / 価格 /
営業時間 / アクセス / 電話導線 / 問い合わせフォーム / 予約導線 / SNS連携 / 地図埋め込み /
title / meta description / OGP / 構造化データ / 更新状況

**2軸を分ける理由**：「評価4.6・レビュー300件・古いHPあり」はリニューアル営業として
非常に重要だが、Lead Score だけでは拾えない。

### Lead Score（0〜100）

| 項目 | 初期配点 |
|---|---|
| レビュー評価（3.0を下限に正規化） | 15 |
| レビュー件数（対数・500件で頭打ち） | 15 |
| HPなし | 25 |
| SNSはある | 10 |
| 電話番号あり | 10 |
| 地域密着ビジネス | 5 |
| 集客型ビジネス | 10 |
| Web改善余地 | 10 |

重みも優先度閾値（S:85 / A:70 / B:55 / C:40）も `lead_score_weights` テーブルから読み、
`/settings` で変更できる。コードには埋め込んでいない。

## 5. 重複排除

照合の優先順位:

1. `source` + `source_business_id`（確実）
2. 電話番号一致 **かつ** 100m以内
3. 店名 + 住所（表記ゆれを正規化して比較）
4. 店名 + 150m以内

**2 に距離条件が入っている理由**：テナントビルの代表番号やチェーン店の本部番号が
複数店舗で共有されているため。電話一致だけで統合すると実在の見込み客が消える。
フリーダイヤル（0120/0570/0800/0990）は照合の根拠として使わない。

統合時は情報量の多い方を優先し、片方にしかない値は必ず残す。
既存レコードの営業メモ・ステータス・Phase 2 の調査結果は上書きしない。

## 6. レジューム

全件調査は数十リクエストに及ぶため、中断時に最初からやり直すとコストが二重にかかる。

- `search_jobs` — ジョブ全体の状態
- `search_subqueries` — 各サブクエリの状態（`pending` / `running` / `completed` / `failed`）とページングカーソル

ページングの途中経過も都度DBに書くので、そこで落ちても次回はそのカーソルから再開できる。
`POST /api/jobs/[id]/resume` は未完了のサブクエリだけを実行する。

予算超過で止まった場合も、そこまでに取得した店舗はすべてDBに残る（部分的成功を捨てない）。

**検証済み**：予算$0.001で停止 → 予算を戻して resume → 続きから完走 → 完了済みジョブの再resumeは何もしない。

## 7. DBスキーマ

`src/lib/db/schema.sql`（SQLite）。Supabase版は `supabase/schema.sql`。

| テーブル | 役割 |
|---|---|
| `businesses` | 店舗マスタ。連絡先は値と出所（`*_source` / `*_source_url`）をセットで保存 |
| `business_history` | 評価・レビュー数・Web状況の変化履歴と、**スコアのスナップショット** |
| `search_jobs` / `search_subqueries` | レジューム可能な調査ジョブ |
| `search_logs` | 検索実行ログ |
| `api_usage` | 予算ガードの根拠となる実使用量。外部APIを叩いた事実は必ずここに1行入る |
| `lead_score_weights` | スコア重みと優先度閾値 |

**スコアのスナップショットが必要な理由**：`businesses.lead_score` を上書きするだけでは
「スコアが高い店は実際に成約したのか」を後から検証できない。
Phase 2 完了時と営業ステータス変更時に、その時点のスコアと内訳を履歴に残している。

## 8. AIの利用範囲

**ルールベース（AI不使用）**
- Phase 1 の数値フィルタすべて
- ポータルドメインの照合（Stage 3）
- 営業パターン A〜E の検出
- Website Opportunity Score の算出

**AI使用（Phase 2のみ・通過分だけ）**
- 独自ドメイン候補が複数あるときの公式サイト最終判定
- 営業理由・強み・弱み・営業角度・推奨オファーの生成
- 電話営業トーク（15秒 / 30秒 / 60秒）・営業メール文面・HP構成案

**ハルシネーション対策**
- プロンプトで「入力にない事実を出力するな。不明なら null か『要確認』」を明示
- 出力は zod スキーマで検証し、失敗したら**前回のエラー内容を添えて**リトライ（最大3回）
- 3回失敗したら `null`。それらしい値で埋めない
- 結果は `sales_analysis_json` に隔離し、UIには「AI生成（要確認）」と表示

## 9. クロールの制約

`PoliteHttpClient`（`src/lib/crawler/httpClient.ts`）が一元管理する。

- `robots.txt` を取得・パースし、`Disallow` されたパスにはアクセスしない
- **robots.txt が取得できなかった場合もアクセスしない**（判断できないなら行かない）
- 同一ドメインへの間隔は最低2秒。`Crawl-delay` がより長ければそちらに従う
- 設定値が2秒未満でも、`env.ts` 側で下限を掛けている
- User-Agent に識別子と連絡先URLを含める
- タイムアウト10秒 / リトライ最大2回（1s, 2s の exponential backoff）
- 4xx は結果が変わらないので即座に返す（無駄なリトライをしない）
- 1店舗あたりのアクセスページ数に上限（デフォルト5ページ）
