# 実装上の判断と、ブリーフからの変更点

ブリーフ（`docs/CLAUDE_CODE_BRIEF.md`）に対して、調査の結果 **前提が変わっていた点** と、
**実装時に自分で決めた点** をまとめる。ここを読めば「なぜこうなっているか」が分かるようにしてある。

---

## 1. ブリーフの前提が現状と合わなくなっていた点（重要）

### 1-1. Web検索APIの無料枠が両方とも消えている

ブリーフ §3-2 / §16-4 は「Google Custom Search か Brave Search のどちらかを無料枠内で使う」
という前提だが、2026年9月時点でこれは成立しない。

| サービス | 現状 |
|---|---|
| Google Custom Search JSON API | **新規申込停止中。2027年1月1日でサービス終了予定。** 既存契約者のみ、無料100クエリ/日 + $5/1,000クエリで利用可 |
| Brave Search API | **2026年2月に新規向け無料プランを廃止。** 現在は従量課金（約$4〜5/1,000クエリ）。新規は月$5のクレジット（約1,000クエリ）のみで、クレジット維持にはBraveへの帰属表示が必要 |

Microsoft の Bing Search API も2025年8月に提供終了しているため、
「無料で使える汎用Web検索API」は実質的に存在しない状態になっている。

**この影響**：Phase 2 Stage 2（店名＋地域名でWeb検索して公式サイト候補を探す）を
無料で回せない。ブリーフの「月$5未満」という目標に対し、Web検索だけで予算を食い切る。

**とった対応**：
- `SEARCH_PROVIDER` のデフォルトを `none` にした。この場合 Stage 2 をスキップし、
  Stage 1（データ提供元のwebsiteフィールド）＋Stage 3/4（ドメイン分類・サイト実測）だけで判定する。
- Google CSE / Brave の実装自体は残してある。契約があるなら環境変数を変えるだけで有効になる。
- Stage 2 が無効なとき、UIとこのドキュメントで「HPなし判定の精度が落ちる」ことを明示している。
  黙って精度が下がるのが一番まずいため。

**判断が必要な点**：Stage 2 を有効にするかどうかは費用対効果の問題なので、
実際に Phase 1 の結果を見てから決めるのがよい。柏市で通過した店舗が180件なら、
Brave の従量課金で約 $0.72〜0.90。月$5の枠内には収まる。

### 1-2. DataForSEO が値上げされている

ブリーフ §3-2 は $0.01/リクエスト + $0.0003/件（柏市1,300件で約$0.41）としているが、
**2026年7月1日に Business Listings が +20% 値上げされ、現在は $0.012 + $0.00036** になっている。

柏市1,300件の再計算：2リクエスト × $0.012 + 1,300件 × $0.00036 = **約$0.49**。

`.env.example` の `DATAFORSEO_COST_PER_*` と `src/config/env.ts` のデフォルトを現行単価に更新した。
単価はまた変わり得るので、契約時に
https://dataforseo.com/pricing/business-data/business-listings-api で再確認すること。

## 3. 実装時に自分で決めたこと

### 3-1. モックプロバイダを「本番同等の経路」として作った

APIキーがない状態でも、検索 → フィルタ → 重複排除 → スコアリング → Phase 2 → AI分析 → CRM →
CSV出力 まで、実際のコードパスを通して動かせるようにした。

理由：ブリーフ §14 は「ステップごとに区切ってレビュー」を求めているが、
データソースの認証情報がないと Step 1 で止まってしまい、その先を一切確認できない。
モックを本物の経路に流すことで、認証情報が揃う前に全体を評価できる状態にした。

モックの店名には `【サンプル】` を付けている。実在店舗の情報を捏造しないため。

### 3-2. OpenStreetMap プロバイダを補助ソースとして追加した

ブリーフ §3-1 のとおり、OSM は評価とレビュー件数を持たないので中核フィルタが成立しない。
そのため**メインのデータソースにはしていない**。ただし完全無料なので、
「評価が要らない用途での$0の下見」として選べるようにしてある。

OSM を選んでいるときは、評価・レビュー件数のフィルタを自動的に無効化する。
そうしないと「評価がnull → 全件フィルタで落ちる → 0件」になってしまうため。

評価・レビュー件数は **null のまま保存する。推定で埋めない。**

> ⚠️ **未検証**：OSM プロバイダは Overpass API のドキュメントに沿って実装しているが、
> この開発環境からは `overpass-api.de` への外部アクセスが遮断されているため、
> **実レスポンスに対する検証ができていない**。同様に DataForSEO も認証情報がないため未検証。
> どちらも初回実行時にレスポンス構造の確認が必要（DataForSEO は zod で検証しているので、
> 構造が違えば静かに壊れず例外になる）。

### 3-3. AIプロバイダに「ヒューリスティック版」を用意した

`AI_PROVIDER=heuristic`（デフォルト）はAPIを一切叩かず、ルールベースで
営業パターン検出・営業トーク・メール文面・HP提案を生成する。

理由：AIキーがないと営業トークが空になり、ツールとして使えなくなる。
テンプレートではあるが、**入力にある事実だけで組み立てる**ので、
ハルシネーションが構造的に起きない。実LLMに切り替えれば、より店舗に即した文面になる。

### 3-4. 予算ガードを「チェック関数」ではなく「呼び出しをラップする関数」にした

ブリーフ §14 Step 2 は「全モジュールが必ず通る場所に置くこと」としている。
これを「呼ぶ前にチェックする」形で実装すると、後からモジュールを足したときに
チェックを忘れた経路ができる。

そこで `BudgetGuard.spend()` が **外部API呼び出しそのものを内側に包む** 形にした。
課金される `fetch` は必ずこの中にあり、記録漏れと未チェックの両方が構造的に防がれる。

検証済み：予算 $0.001 で DataForSEO を叩かせたところ、
**取得0件・実コスト$0・外部への通信なし** で停止し、ジョブは再開可能な状態で残った。

### 3-5. 「未確認」を空欄と区別した

電話・メールが見つからない場合、UIとCSVで **「未確認」と明示**する。
空欄にすると「まだ調べていない」のか「調べたが無かった」のか区別できず、
営業時に「この店は本当にメールが無いのか？」を毎回調べ直すことになる。

### 3-6. 無料ホスティングを「独自HP」として数えない

Wix / Jimdo の無料枠、`business.site`、`crayonsite` 等のドメインは、
独自ドメインではないので `official` に分類していない。
これらは作り直し提案の対象になりやすいため、営業機会あり側に倒すのが実務的だと判断した。

### 3-7. 電話番号の照合に「距離」を必須にした

ブリーフ §10-1 の指摘どおり、テナントビルの代表番号やチェーン店の本部番号が
複数店舗で共有されているケースがある。電話一致だけで統合すると、
**営業リストから実在の見込み客が静かに消える**。

そこで「電話一致 **かつ** 100m以内」を統合の条件にした。
座標が取れない場合は「電話一致 かつ 店名一致」に落とす。
さらにフリーダイヤル（0120/0570/0800/0990）は照合の根拠として使わないようにしている。

### 3-8. 営業ファネルの集計を「履歴ベース」にした

「架電数」を現在のステータスで数えると、電話済 → 成約 と進んだリードが
架電数から消えてしまい、成約率の分母が壊れる。
`business_history` の `status_changed` イベントから数えるようにした。

### 3-9. Lead Score の評価正規化を rating/5 から変えた

`rating / 5` をそのまま使うと、評価3.0の店でも配点の60%が入ってしまい差がつかない。
実質的な下限を3.0に置き、3.0〜5.0を0〜1に伸ばしている。
検索の最低評価が3.7なので、3.0未満はそもそもリストに入らない。

## 4. 意図的にやらなかったこと

| やらなかったこと | 理由 |
|---|---|
| Supabase Auth / RLS | 個人利用と確認したため。スキーマ（`supabase/schema.sql`）は残してあるので、必要になったら適用できる |
| 営業メールの自動送信 | ブリーフ §2-4 で明示的に禁止。メールの取得・表示までにとどめている |
| Google Places API の利用 | ブリーフ §3-1 のとおり、規約上コンテンツを保存できず本アプリのアーキテクチャが成立しない |
| Google Maps のスクレイピング | ブリーフ §2-2 で禁止。例外なし |
| 連絡先の推測生成 | ブリーフ §2-3 で禁止。見つからなければ null |
| Vercel へのデプロイ設定 | ブリーフ §4-2 のとおりローカル実行を推奨。デプロイ可能な構成自体は維持している |

## 5. 次にやるとよいこと

1. **DataForSEO の疎通確認**（`npm run check:dataforseo`）
   実レスポンスを見て `DataForSEOProvider.toCandidate()` のフィールド対応を確定させる。
   zodスキーマがあるので、想定と違えばエラーで分かる。
2. **Stage 2（Web検索）を有効にするかの判断**
   Phase 1 の通過件数が見えてから、Brave の従量課金が予算に見合うかを決める。
3. **Lead Score の重み調整**
   実データが100件ほど溜まったら、優先度Sの分布を見て `/settings` から閾値を調整する。
4. **成約データが溜まってからのスコア検証**
   `business_history` にスナップショットが残っているので、
   「成約した店のPhase2完了時スコア」の分布を見れば、重み付けが妥当だったかを検証できる。

## 6. 再チェックで見つかった不具合と修正（2026-09-14）

実装後に全体を通しで再点検し、実際に動かして確認できた不具合を修正した。
以下はすべて回帰テストを追加してあるので、同じ形で再発しない。

### 6-1. Phase 2 が永久に 0 件になっていた（重大）

未調査の店舗を選ぶとき、`LIMIT 25` してから JS 側で「未調査のもの」を絞っていた。
Lead Score の上位25件が調査済みになった時点で対象が 0 件になり、
**「10件ずつ調査する」を何度押しても1件も進まない**状態になっていた。

再現：調査済み30件・未調査500件のDBで、対象が0件になることを確認。
修正：SQL の WHERE 句で未調査を絞ってから LIMIT する。`listBusinesses({ phase2Done: false })`。

### 6-2. 未調査件数が1,000件を超えると過小報告されていた

「全行を取得して JS で数える」実装だったため、取得上限の1,000件で頭打ちになっていた。
1,130件のDBで「970件」と表示されることを確認。COUNT クエリに置き換えた。

### 6-3. スキーマ変更が既存DBに反映されず、起動後に落ちていた（重大）

`schema.sql` は `CREATE TABLE IF NOT EXISTS` なので、
**既にテーブルがある場合、後から追加したカラムは作られない。**
この状態でアプリを更新すると `no such column` で実行時に落ちる。
実際にこの再チェック中に発生した。

DBを作り直せば直るが、それは集めた店舗と営業メモを捨てることになるので、
`src/lib/db/migrate.ts` を追加した。起動時に現在のカラムを読んで、
足りないものだけ `ALTER TABLE ADD COLUMN` する。既存データは保持される。

検証：44店舗・営業ステータス4件が入った古いDBに対して実行し、
カラムが追加され、店舗数・ステータス・メモがすべて残ることを確認した。

**新しいカラムを `schema.sql` に足したら、`migrate.ts` の表にも1行足すこと。**

### 6-4. Phase 2 が実行時間の上限を超えていた

1店舗あたり robots.txt + 最大5ページ + 公式サイト判定3回 = 9リクエスト。
2秒間隔なので18秒かかる。これを25件回すと7.5分で、`maxDuration = 300秒` を突き抜ける。
プロセスごと殺されるので「何件終わったか」もクライアントに返らない。

`phase2Batch.ts` に締め切りを持たせ、残り時間が1店舗分を切ったら
自分で打ち切って残件数を返すようにした。

### 6-5. 検索条件が2つ、どこからも読まれていなかった

`includeSnsOnly`（SNSのみの店舗を含む）と `requireEmail`（メールがある店舗のみ）は、
型にもUIにもあるのに、**実装のどこからも参照されていなかった**。
チェックボックスが黙って無効だった。

どちらも Phase 1 の時点では判定できない（SNSもメールも調査後に分かる）ので、
`passesPostEnrichFilter()` として Phase 2 の後に適用し、
UIには「Phase 2 の調査後に判定されます」と明記した。

### 6-6. 全角の電話番号が重複排除から漏れていた

候補検索の SQL が `replace(replace(phone,'-',''),' ','')` という素朴な正規化で、
`normalizePhone()` の結果と一致しなかった。`０４－７１６７－１１１１` のような
全角表記や `(代表)` 付きの番号が候補に上がらず、重複が残っていた。

`phone_normalized` カラムを追加し、書き込み時に `normalizePhone()` を通した値を保存、
照合はそちらで行うようにした（インデックスも効くようになった）。

### 6-7. 検索ログのWeb検索費・AI費が 0 固定だった

有料APIを使い始めた途端に「どこにいくら使ったか」が追えなくなる状態だった。
`api_usage` からジョブ単位で種別別に集計して記録するようにした。

### 6-8. `npm run lint` が対話プロンプトで固まっていた

`next lint` は Next.js 15 で非推奨（16で削除）で、ESLint の設定もなかったため、
実行すると設定ウィザードが起動して止まっていた。CIに入れたら詰まる。

ESLint flat config（`eslint.config.mjs`）に移行した。
移行した直後に実際のバグが2件見つかっている：
未使用 import と、`<a href="/leads">` によるフルリロード（`next/link` にすべき箇所）。

### 6-9. 一覧画面が毎回全行を2回読んでいた

サマリーの4つの数字のためだけに最大5,000行を取得してJSで数えていた。
`getLeadSummary()` として1クエリの集計に置き換えた。

### 6-10. 営業ツールとしての導線が弱かった

- 電話番号が本文中の小さいリンクだった → カード内で最も押しやすい黒いボタンにした
- 営業トークが全部折りたたみだった → 30秒トークだけ開いた状態で出すようにした
  （「ワンクリックで電話営業に移れる状態を作る」のが目的なので）
- AI の一言理由が**44店舗すべて同じ文言**で、カードの1/4を占めて情報量ゼロだった
  → パターン・評価・口コミ数・SNS有無・改善余地から組み立て、店舗ごとに変わるようにした
- HPがない店舗に「サイト未調査のため弱点は要確認」と出ていた（事実として誤り）
  → 「公式サイトがないため、検索から来た人が情報を確認できない」に修正

## 7. 有料前提での構成（推奨）

「多少なら有料でもよい」という前提で再検討した結果、**Stage 2 は DataForSEO の SERP API を使うのが最適**。

| 選択肢 | 単価 | 問題 |
|---|---|---|
| **DataForSEO SERP（Live）** | **$0.002/クエリ** | **なし。Business Listings と同じアカウント・同じ請求・同じ予算ガード** |
| DataForSEO SERP（標準キュー） | $0.0006/クエリ | 即時応答しないので対話的な利用には不向き |
| Brave Search | 約$4〜5/1,000クエリ | 別アカウント・別請求。1クエリ/秒の制限 |
| Google Custom Search | — | **新規申込不可**（2027年1月終了予定） |

`SEARCH_PROVIDER=dataforseo` で有効になる。認証情報は Business Listings と共用なので追加設定は不要。

### 柏市を全件調査した場合の総額（現行単価）

| 段階 | 内訳 | 金額 |
|---|---|---|
| Phase 1 | 2リクエスト × $0.012 + 1,300件 × $0.00036 | $0.49 |
| Phase 2 Stage 2 | 通過180件 × $0.002 | $0.36 |
| AI | Gemini無料枠なら $0 / 有料でも 180 × $0.0005 | $0〜0.09 |
| クロール | 自前・通信費のみ | $0 |
| **合計** | | **約 $0.85〜0.94** |

月間予算 $5 の範囲で、柏市を全件調査して周辺市町村にも手が届く。
`MONTHLY_BUDGET_USD` と `PER_SEARCH_BUDGET_USD` は実額に合わせて上げておくこと
（デフォルトの `PER_SEARCH_BUDGET_USD=1` だと全件調査の途中で止まる）。

## 8. 営業手順とアプローチの実装（2026-09-14）

「リストを作る道具」ではなく「電話をかけさせる道具」にするため、
営業の手順とアプローチをアプリの中に入れた。別資料にすると読まれないため。

### 8-1. 売るものを2系統としてモデル化した

当初の実装は「HP制作」1系統しか知らず、提案が常に
「1ページ型 / 5ページ型 / 予約対応型 / 集客特化型」のどれかになっていた。
実際のサービスは **公式サイト（HP）と販売ページ（LP）** の2系統あり、目的が違う。

| | 公式サイト | 販売ページ（LP） |
|---|---|---|
| 目的 | 店名で検索されたときの受け皿 | 1つの商品・コースを売り切る |
| 性質 | 常設。信頼性と基本情報 | 行動は1つだけ。広告から直接送れる |

これを分けないと提案がずれる。SNSで集客できている整体院に5ページのHPを出しても
「今で足りてる」で終わるが、「初回体験の申込ページ」なら来月の予約数の話になる。

`src/config/offerings.ts` に7プラン（サイト4・LP3）を定義し、
それぞれに「どういう店に向くか」「相手にとっての価値」「納品物」「期間」を持たせた。

**価格は意図的に空にしてある。** 運用者ごとに違う数字を勝手に埋めて画面に出すと、
それが相手に伝わる金額になってしまうため。`PRICE_HINTS` を設定するまで「未設定」と表示する。

### 8-2. 何を提案するかをルールベースで自動判定する

`src/lib/scoring/nextAction.ts` が、業種とWeb状況から第一提案を決める。
AIを設定していなくても必ず出るので、$0構成でも営業に使える。

判定の要点（Web状況が業種の標準提案を上書きする）：
- 古いサイトがある → **リニューアルが最優先**。ゼロから作るより話が通りやすい
- サイトが整備済み → **サイトの提案は通らない**のでLPに切り替える
- SNSのみ → **1ページ型から**入る。最小構成の方が通しやすい

### 8-3. 業種ごとの切り口を表にした

「ホームページを作りませんか」はどの業種にも同じように弱い。
相手が困っているのはWebではなく商売の方なので、
**その業種で実際に起きている取りこぼし**から入る必要がある。

例：飲食店に「SEO対策を」では刺さらないが、
「ポータル経由のご予約だと手数料がかかりますよね」なら話が始まる。

`src/config/approaches.ts` に11業種分の
「起きている取りこぼし」「電話の切り口」「この業種での注意点」を定義した。
注意点には広告規制（医療広告ガイドライン・柔整法・各士業会の広告規程・景表法・特商法）を含めている。

### 8-4. 断り対応を「食い下がる技術」にしなかった

よくある断り文句7種に対して、意味・返し方・**引くべきサイン**を書いた。
引くべきサインを必ず添えているのは意図的で、
相手が本当に不要なら引くのが正しい判断だから。
1件に粘る時間で3件かけた方が成果が出るし、地域で商売をする以上は評判の方が長期的に効く。

### 8-5. 数値目標を書かなかった

営業手順に「成約率◯%を目指す」といった数字は入れていない。
実測が溜まる前に目標値を書くと、根拠のない基準として一人歩きするため。
自分の実数は `/metrics` のファネルで見る。

### 8-6. 手順に必ず「なぜ」を添えた

各ステップに「なぜそうするか」と「よくある失敗」を必ず付けている。
手順だけ書いた資料は理由が分からないので形骸化する。
特にステップ5（すぐ記録する）は、飛ばすとスコアのスナップショットが残らず、
「どのスコアの店が成約したか」の検証が永久にできなくなる。

## 9. メールアドレスの一覧表示（2026-09-14）

### 9-1. 「メールあり」ではなくアドレスそのものを出す

一覧のカードは「メールあり」とだけ表示していた。これだと結局リードを開かないと
アドレスが分からず、メールで営業するときに1件ずつ詳細を開くことになる。

アドレスそのものを出し、ワンタップでコピーできるようにした。
一覧のフィルタにも「メールあり」を追加した（以前は検索条件にはあったが一覧側になかった）。

アドレスにマウスを乗せると **どのページで確認したか** が出る。
推測生成していないことを、その場で確認できるようにするため。

### 9-2. モックモードでメール抽出が一度も動いていなかった

モックプロバイダが返すサイトURLは `https://example-<seed>.test/` という
到達不能なアドレスだった。そのため Phase 2 の
「サイト品質の実測」も「公開メールの抽出」も一度も実行されず、
**Website Opportunity Score は常に100、メールは常に未確認**という状態だった。

つまり「すぐ試せます」と言いながら、Phase 2 の中身は確かめられなかった。

そこで `/api/mock-site/[id]` を追加し、アプリ自身がサンプル店舗のHTMLを配信するようにした。
クローラは本物として robots.txt を確認し、HTMLを解析し、`mailto:` からアドレスを拾う。
**通る経路は本番と完全に同じ。**

店舗ごとにサイトの出来を3段階に変えてあるので、
改善余地スコアにも差が出る（実測で21〜56に分布することを確認）。

メールのドメインは `.test`（RFC 2606 の予約TLD、実在し得ない）に固定した。
実在する誰かのアドレスに偶然一致しないようにするため。

**データを捏造しているわけではない**点は重要で、
抽出されたアドレスは実際にクロールしたページに実際に書かれているものである。
DBに直接ダミーを流し込む実装にはしていない。

### 9-3. クロール間隔にループバック例外を入れた

モック店舗サイトは全部同じホスト（127.0.0.1）にあるので、
2秒間隔をそのまま適用すると25件の調査に5分以上かかり、実行時間の上限に当たる。

2秒間隔の制限は **他人のサーバーに負荷をかけない** ためのものなので、
自分自身のプロセスを叩くときに守る理由がない。
`isLoopbackHost()` で判定し、ループバック宛だけ間隔をスキップする。

判定は厳格にしてある（`localhost.example.com` や `notlocalhost` を
誤ってループバック扱いすると、よそのサーバーへの制限が抜けるため）。
テストで外部ホストが除外されないことを確認している。

### 9-4. モックサイトのホストに localhost ではなく 127.0.0.1 を使う

これは §6 で入れた修正の副作用。
`extractHostname()` は「ドットを含まない文字列はホスト名として扱わない」ようにしてある
（日本語の文が punycode のホスト名に化けるのを防ぐため）。
`localhost` はこの判定に引っかかり、公式サイトとして認識されなかった。

ホスト名の検証を緩めるのではなく、モック側を `127.0.0.1` にした。
検証を緩めると、本来弾きたいゴミURLが公式サイト扱いされてしまう。

## 10. 価格設定（2026-09-14）

### 10-1. 相場

| 依頼先 | 制作費 | 月額保守 |
|---|---|---|
| 大手制作会社 | 300万円〜 | 5万円〜 |
| 中小制作会社 | 80〜150万円 | 1〜3万円 |
| フリーランス | 10〜50万円 | 5,000〜1万円 |
| 自作・サブスク型 | 0〜10万円 | 2,600円〜 |

LP1ページ単体は平均発注額55.4万円・中央値40万円。
10万円以下は「フリーランスか個人にしか頼めない」価格帯とされている。
月額保守はサーバー管理のみで5,000円前後、更新対応込みで1〜3万円。

### 10-2. 「実績がないから安く」を採らなかった理由

4つある。

**時給が破綻する。** 1ページでも先出し制作1〜2h + 電話とやり取り2〜3h + 修正2h + 公開1h で
6〜8時間かかる。¥98,000 なら時給14,000円で専門職として成立するが、
¥30,000 だと時給4,300円で、営業時間を足すと事業として続かない。
実績を作る前に消耗して辞めることになる。

**値上げができなくなる。** 最初の客に付けた価格は、その人の紹介客にも引き継がれる。
紹介が回り始めた瞬間に価格が固定されるので、安易な値下げが後から効いてくる。

**安い客ほど手がかかる。** 最も値切る客が、最も写真を出さず、最も修正を要求し、
最も音信不通になる。サービス業で繰り返し観測される力学。

**リスク除去は先出しで済んでいる。** これが一番大きい。
完成品を見てから決められる時点で、相手のリスクは既にゼロ。
そこへ低価格を重ねるのは、持っているカードを二重に切ることになる。
安くすべきは価格ではなく入口のハードルで、この2つは別物。

### 10-3. 月額ありを主力にした理由

- 入口の数字が7万円低い（¥98,000 vs ¥168,000）
- 店主はサーバー・ドメイン・SSLの管理ができないので、結局必要になる
- 継続収入が残る。一件ごとに新規を探し続ける構造から抜けられる

買い切りは、サブスクを嫌う層（年配の店主に多い）向けの受け皿として残した。
初年度の総額が両者でほぼ並ぶようにしてあるので、どちらを選んでも損得が極端にならない。

**月額を提示するときは初年度の総額も併記する。**
月額だけ見せて総額を隠すのは不誠実で、後から気づかれたときに関係が壊れる。
UIにも総額を出すようにした。

### 10-4. 割引は理由と件数を明示する形にした

無条件に安くすると戻せないが、
「柏市での事例を作りたいので、制作事例として掲載させていただける場合に限り最初の5件まで」
なら、6件目から通常価格に戻しても筋が通る。

`INTRO_OFFER` に理由・条件・件数・割引率を持たせ、割引後の金額は1,000円単位で丸めている
（端数が残ると「値引きした感」ではなく「雑な見積もり」に見える）。

### 10-5. 「無料」という打ち出しをやめた

公開時に費用が発生する構成になったため、「無料でHPを作ります」は
景品表示法の有利誤認表示にあたる可能性がある。文面から削除した。

代わりに訴求するのは **「見るのは無料・気に入らなければ削除」** という事実。
これは実際にそうなので問題がなく、しかも先出しの強みそのものなので訴求力も落ちない。

テストで、文面に「無料で作」「無料でお作り」「無料で制作」が含まれないことを固定している。

### 10-6. 補助金は営業材料として扱うが、断定しない

小規模事業者持続化補助金のウェブサイト関連費は補助率2/3・上限30万円。
¥98,000 なら実質負担が約3.3万円になる計算で、価格の話が軽くなる。

ただし **ウェブサイト関連費のみでの単独申請はできず**、他の販路開拓費と組み合わせる必要がある。
要件は公募回ごとに変わるため、文面は「対象になる可能性があります」までにとどめ、
商工会議所での確認を案内する形にした。採択を保証する書き方はテストで禁止している。
