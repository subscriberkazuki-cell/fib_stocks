# ここから下が Claude Code への指示本文

## 1. プロジェクト概要

「LocalWeb Hunter」というWebアプリケーションを開発する。

**一行で言うと**：Google Maps由来の公開ビジネス情報を起点に、「評価は高い（＝商売は成立している）が、Web上の営業基盤が弱い（＝公式HPがない／古い）」地域店舗を自動発掘し、ホームページ制作営業の見込み客リストと営業優先順位を生成するツール。

**最終目的は「店舗検索ツール」ではない。「営業マシン」である。**
単に店舗を集めるのではなく、「この店にHPを提案する価値が高い」と判断できる店舗をランキングし、ユーザーが短時間で電話営業に移れる状態を作ることが最重要。

初期対象地域は千葉県柏市。将来的に周辺市町村 → 千葉県 → 関東 → 全国へ拡張する。

## 2. 絶対に守るべき制約（最優先。これに反する実装は却下）

### 2-1. コスト制約
- **可能な限り無料で構築する。** 有料が避けられない箇所のみ、最小コストで設計する。
- ユーザーの許容コスト感：柏市全域の初回スキャンで **$1未満**、月間ランニングで **$5未満** を目標とする。
- 実装には必ず **ハードコストキャップ** を入れる。月間予算（環境変数 `MONTHLY_BUDGET_USD`、デフォルト $5）を超えたら、外部API呼び出しを**例外を投げて停止**する。警告表示だけでは不可。
- 検索実行前に「この検索の推定コストは $X です」を必ずUIに表示し、ユーザーの明示的な確認を経てから実行する。

### 2-2. データ取得の制約
- **Google Maps のWebページを Playwright / Puppeteer / Selenium 等で直接スクレイピングする実装は禁止。** 例外なし。
- ビジネスデータの取得は必ず `BusinessDataProvider` インターフェース経由で行う。アプリ本体（スコアリング・UI・DB層）が特定プロバイダの実装を直接importしてはならない。
- 店舗の公式サイトへのHTTPアクセス（サイト品質評価・メール抽出）を行う際は、必ず以下を守る：
  - `robots.txt` を取得して確認し、`Disallow` されているパスにはアクセスしない
  - リクエスト間隔は同一ドメインに対して最低2秒空ける
  - User-Agent に識別可能な文字列と連絡先URLを含める（例: `LocalWebHunter/0.1 (+https://example.com/about)`）
  - タイムアウト10秒、リトライは最大2回（exponential backoff）

### 2-3. データ捏造の禁止
- **電話番号・メールアドレスを推測生成することは絶対禁止。**
  - 「店名からドメインを推測して `info@` を生成する」ような実装をしてはならない
  - 公開情報として実際に確認できたものだけを保存する
  - 見つからない場合は `null` を保存し、UIには「未確認」と表示する
- AIが生成した推定値と、実データを**必ずスキーマレベルで分離**する。
  - 例: `rating` は実データ、`estimated_customer_value` はAI推定値 → 後者は `*_type = 'AI_ESTIMATE'` を必ず付与
- すべての重要フィールドに出所（`*_source`）を記録する。出所不明の値は保存しない。

### 2-4. 個人情報・法令
- 公開情報のみを使用する。個人情報を不必要に収集しない。
- 個人の私的なメールアドレス（`gmail.com` 等のフリーメールで、かつ事業用と判断できないもの）は営業目的で収集・蓄積しない。除外ロジックを実装すること。
- **初期バージョンでは営業メールの自動一斉送信機能を実装しない。** メールアドレスの「取得・表示」までに留める。
- 日本の個人情報保護法上、個人事業主（整体院、士業事務所等）の連絡先は個人情報に該当し得る。利用目的（HP制作営業の見込み客管理）を明示するページを最低限用意すること。

## 3. データソース戦略（ここが設計の心臓部・調査済みの結論）

### 3-1. 結論：DataForSEO Business Listings API を使う（少額有料）

**なぜ Google Places API（無料枠あり）を使わないか — 重要**

Google Maps Platform の Places API には無料枠があるが、**利用規約上、この用途では使えない**。

- Google Maps Platform の規約は、Places API のコンテンツを事前取得・キャッシュ・保存することを禁止している。例外は `place_id`（無期限保存可）と緯度経度（30日まで）のみ。
- 評価・レビュー件数・電話番号・ウェブサイトURL・店名は、**すべて保存が許されない**。ライブで取得して Google の帰属表示とともに表示する前提のデータである。
- 本アプリの中核（店舗マスタDB、Lead Score の永続化、営業ステータス管理、CSV出力、評価の変化履歴）は、これらを保存することが前提になっている。つまり **Google Places API を使うと、このアプリのアーキテクチャそのものが規約違反になる**。

したがって Google Places API 直利用は選択肢から外す。Google Maps のスクレイピングは §2-2 で禁止済み。

**なぜ OpenStreetMap（完全無料）だけでは足りないか**

OSM / Overpass API は完全無料でライセンスも寛容（ODbL）だが、**評価とレビュー件数を持っていない**。本アプリの中核フィルタは「評価3.7以上・レビュー5件以上」であり、これが取れないと「商売が成立している店舗」を絞り込めない。ランキングの根拠が消える。

ただし OSM は補助的に有用なので、以下の用途で**無料の補助ソースとして併用**すること：
- 業種カテゴリの補完
- 住所・座標の検証
- 重複排除の照合材料

### 3-2. 採用するデータソース構成

| 用途 | サービス | コスト | 備考 |
|---|---|---|---|
| 店舗発見・評価・レビュー数（Phase 1） | DataForSEO Business Listings API | $0.01/req + $0.0003/件 | 1リクエスト最大1,000件 |
| 公式サイト候補の探索（Phase 2 Stage 2） | Google Custom Search JSON API または Brave Search API | 無料枠内 | どちらも無料枠あり。実装前に現在の無料枠を確認すること |
| サイト品質評価・メール抽出 | 自前HTTPクローラ（httpx + BeautifulSoup + trafilatura） | 無料 | §2-2 のクロール規約を厳守 |
| AI判定・営業トーク生成 | Google Gemini API（無料枠） | 無料枠内 | 環境変数で OpenAI / Anthropic に切替可能にする |
| DB / Auth | Supabase Free | 無料 | |
| ホスティング | 後述 §4-2 参照 | 無料 | |

**柏市Phase 1の実コスト試算**：約1,300件取得の場合、リクエスト2回 + 1,300件 = $0.02 + $0.39 = **約$0.41**。
Phase 2（通過した約180件のみ）は検索・AIとも無料枠で吸収可能な見込み。

**重要**：DataForSEO の単価は変わり得る。実装時に必ず https://dataforseo.com/pricing/business-data/business-listings-api で現在の単価を確認し、`costEstimator.ts` の定数に反映すること。

### 3-3. 【判断が必要】完全無料に振る場合の代替案

もしユーザーが「1円も払いたくない」と判断した場合の代替構成も理解しておくこと。ただしこの場合、以下の機能が**成立しなくなる**ことを実装前に明示すること：

- 店舗マスタDBへの評価・電話・サイトURLの永続保存（規約違反になる）
- CSV出力（Googleコンテンツの書き出しになる）
- 評価・レビュー数の変化履歴
- オフラインでのバッチスコアリング

この場合の妥協案は「`place_id` と自前の営業メモ・ステータスのみDB保存し、表示のたびにGoogle Places APIからライブ取得する」形になるが、一覧表示のたびに無料枠を消費し、営業リストとしての実用性は大きく下がる。

**デフォルトでは §3-2 の構成（DataForSEO・約$0.41）で実装すること。**

## 4. 技術スタック

### 4-1. 確定事項
- **Frontend**: Next.js 15 (App Router) + TypeScript (strict) + Tailwind CSS
- **Backend**: Next.js API Routes / Server Actions
- **サイト解析部分のみ**: Python（httpx / BeautifulSoup / trafilatura）または Node.js（cheerio + undici）
  - → **Node.js 実装を推奨**。理由：デプロイ先を1つに統一でき、無料枠の管理が単純になる。Pythonが必要な理由が出てきたら相談すること。
- **Database**: Supabase (PostgreSQL) — Free tier
- **Auth**: Supabase Auth
- **AI**: プロバイダ抽象化（`AIProvider` インターフェース）。デフォルト実装は Gemini。環境変数 `AI_PROVIDER` で切替。

### 4-2. ホスティング（要注意）
- Vercel Hobby プランは**非商用利用が前提**とされている。本アプリは営業活動に使うため、商用利用と判断される可能性がある。
- 対応方針（優先順）：
  1. **ローカル実行**（`npm run dev` / `npm run build && npm start`）— 個人の営業ツールとしては最も確実で完全無料
  2. Cloudflare Pages / Workers の無料枠
  3. 商用利用が問題になるならVercel Proへ（$20/月）
- **デフォルトはローカル実行前提で作る**。ただしデプロイ可能な構成は維持しておくこと（環境変数の扱い等）。

### 4-3. セキュリティ
- APIキーは絶対にクライアントに露出させない。すべてサーバーサイドでのみ使用する。
- Supabase の `SERVICE_ROLE_KEY` はサーバーサイドのみ。クライアントには `ANON_KEY` のみ。
- Supabase の Row Level Security (RLS) を有効化し、ユーザーは自分のデータのみアクセス可能にする。
- 検索回数のレート制限を実装する（異常な大量検索の防止）。

## 6. 2段階データ取得フロー（コスト最適化の中核）

```
[検索条件入力]
   ↓
[推定コスト表示 → ユーザー確認]
   ↓
Phase 1: 安い一次スクリーニング（DataForSEO）
  取得: 店名 / カテゴリ / 評価 / レビュー件数 / 座標 /
        business_id / 電話（あれば） / website有無
   ↓
[ルールベースでフィルタ ← AIを一切使わない]
  rating >= 3.7 AND review_count >= 5 AND website候補なし
   ↓
[重複排除]
   ↓  ← ここを通過した件数のみが Phase 2 に進む
Phase 2: 高コスト調査（通過分のみ）
  - Web検索で公式サイト候補を探索
  - サイト品質解析
  - メール抽出（公開情報のみ）
  - AI判定（分類・スコアリング・営業トーク生成）
   ↓
Lead Score / Website Opportunity Score 算出
   ↓
営業優先度 S/A/B/C/D 付与 → 一覧表示
```

**この2段階分離は絶対に崩さないこと。** Phase 1 を通過しない店舗には、Web検索コストもAIコストも一切かけない。これが無料〜低コストを成立させる唯一の仕組みである。

**AIを使う箇所 / 使わない箇所の切り分け**：
- ルールベース（AI不使用）：数値フィルタ、`website_url == null` の一次判定、ポータルドメインの照合
- AI使用（Phase 2のみ）：曖昧な業種分類、公式サイトかどうかの最終判定、サイト品質の定性評価、営業優先度・営業理由・営業トークの生成、店舗タイプ分類

## 7. 「ホームページなし」判定ロジック（最重要機能）

`website_url == null` だけで判定してはならない。以下の4段階で判定する。

**Stage 1**: ビジネスデータAPIに公式website URLが存在するか → 無ければ Stage 2 へ

**Stage 2**: 「店名 + 市区町村名」でWeb検索し、候補URLを収集

**Stage 3**: 候補URLをルールベースで分類。以下は「公式ホームページではない」と判定する：
- SNS: Instagram / Facebook / X(Twitter) / TikTok / LINE
- 地図・プロフィール: Google Maps
- グルメ・美容ポータル: 食べログ / ホットペッパー（beauty含む）/ ぐるなび / Retty / EPARK
- 予約・EC: 楽天 / Amazon / Yahoo!ショッピング / 一休 / じゃらん
- 求人: Indeed / タウンワーク / バイトル
- その他ポータル: エキテン / まいぷれ / iタウンページ

独自ドメインまたは店舗独自の公式サイトが確認できた場合のみ「公式サイトあり」。
判定が曖昧なケースはAIに最終判定させる（§9参照）。

**ドメインリストはコードにハードコードせず、設定ファイル（`config/portalDomains.ts`）に配列で切り出す**こと。運用しながら追加していくため。

**Stage 4**: 公式サイトが存在する場合でも除外しない。品質を評価し、営業機会があれば候補に残す。

### Web Presence Score（0〜100、高いほど営業対象として有望）
| スコア | 状態 |
|---|---|
| 0 | 公式サイトあり・十分整備 |
| 20 | 公式サイトありだが非常に古い・情報不足 |
| 40 | SNSのみ |
| 50 | ポータルサイトのみ |
| 60 | 複数のポータルサイトのみ |
| 80 | Google等の店舗プロフィールのみ |
| 100 | 独自HPなし＋Web情報も極めて少ない |

## 8. スコアリング仕様

### 8-1. Lead Score（0〜100）
「HP制作営業に向いている店舗」をランキングする。単純に評価が高い店舗を上位にしてはならない。

デフォルト配点（合計100点）：
| 項目 | 配点 |
|---|---|
| レビュー評価 | 15 |
| レビュー件数 | 15 |
| HPなし | 25 |
| SNSはある | 10 |
| 電話番号あり | 10 |
| 地域密着ビジネス | 5 |
| 集客型ビジネス | 10 |
| Web改善余地 | 10 |

**重みは設定画面から変更可能にすること。** DBの `lead_score_weights` テーブルから読み込み、ハードコードしない。
レビュー件数は青天井なので対数スケールで正規化する（500件で頭打ち）。

### 8-2. Website Opportunity Score（0〜100）— Lead Scoreとは別軸
公式サイトがあっても営業機会があるかを測る。評価項目：
独自サイトの有無 / SSL / モバイル対応 / 表示速度 / デザイン品質 / 情報量 / 店舗写真 / メニュー・サービス情報 / 価格情報 / 営業時間 / アクセス / 電話導線 / 問い合わせフォーム / 予約導線 / SNS連携 / Google Maps連携 / SEO基本設定（title, description, OGP, 構造化データ）/ 更新状況

**この2軸を分ける理由（重要）**：
- 「評価4.7、レビュー200件、Instagram活発、HPなし」→ 最優先ターゲット
- 「評価4.0、レビュー5件、HPなし」→ 営業価値は低い
- 「評価4.6、レビュー300件、古いHPあり」→ **リニューアル営業として非常に重要**（Lead Scoreだけでは拾えない）

### 8-3. 営業優先度 S/A/B/C/D
Lead Score から変換する。初期閾値は S:85+ / A:70+ / B:55+ / C:40+ / D:40未満。
**実データが溜まったら分布を見て調整できるよう、閾値も設定値として外出しすること。**

### 8-4. AIによる営業機会検出パターン
以下のパターンをAIが優先的に検出できるようにする：
- パターンA: 評価4.5以上 + レビュー100件以上 + HPなし → 最優先
- パターンB: 評価4.5以上 + レビュー300件以上 + 古いHP → リニューアル営業
- パターンC: SNSフォロワー多い + HPなし → SNS→公式HP導線提案
- パターンD: 予約型業態 + HPなし → 予約導線構築提案
- パターンE: 高単価業態 + HPなし → 高単価HPプラン提案

## 9. AIの利用仕様

### 9-1. 公式サイト判定AI
- Input: 店舗名 / 住所 / 電話番号 / URL / ページタイトル / ページ本文 / ドメイン / SNS情報
- Output: `official_site_probability` (0〜1) / `reason` / `matched_business_name` / `matched_phone` / `matched_address` / `site_type` (official / portal / social / booking / marketplace / unknown)

### 9-2. 店舗タイプ分類AI
高単価型 / 地域密着型 / リピート型 / 新規集客型 / SNS集客型 / 店舗ブランド型 / 専門サービス型 / 予約型 / 緊急需要型 / EC併用型 から分類し、「HPを導入すると効果が大きそうな理由」を1〜3文で生成する。

### 9-3. 営業提案AI
各リードについて生成する：
- `score`（100点満点の営業価値）/ `reason` / `strengths` / `weaknesses` / `sales_angle` / `recommended_offer` / `estimated_priority`
- 電話営業トーク：15秒版 / 30秒版 / 60秒版
- メール営業文（店舗ごとに個別化）
- HP提案内容：1ページ型 / 5ページ型 / 予約対応型 / 集客特化型

### 9-4. ハルシネーション対策（必須）
- AIへのプロンプトで「入力に含まれない事実を出力してはならない。不明な項目は `null` または `"要確認"` と出力すること」を明示する。
- 出力は必ず構造化（JSON schema）で受け取り、パースに失敗したらリトライ。3回失敗したらそのフィールドを `null` にする。
- AI出力は必ず `*_type = 'AI_ESTIMATE'` としてマークし、実データと混在させない。
- 将来のHP自動生成機能でも同じ原則を適用する。未知の情報は勝手に埋めず「要確認」とする。

## 10. データベース設計

既存の `supabase/schema.sql` をベースにする。以下を必ず含めること：

- `businesses` — 店舗マスタ。全フィールドに `*_source` を持たせる
- `business_history` — 評価 / レビュー数 / website_status / lead_score の変化履歴
- `search_logs` — 検索日時 / 地域 / カテゴリ / 検索件数 / API使用量 / コスト / 新規件数 / 重複件数
- `lead_score_weights` — スコア重み設定
- `api_usage` — 日次・月次のAPI使用量とコスト（予算ガード用）

### 10-1. 重複排除の優先順位
1. `place_id` / `business_id`
2. 電話番号
3. 店名 + 住所
4. 店名 + 緯度経度

**電話番号での照合には落とし穴があるので注意**：
- 正規化してから比較する（ハイフン除去、国番号統一、先頭0の扱い）
- **テナントビル内の複数店舗やチェーン店の本部番号が同一のケースがある。** 電話番号一致だけで統合せず、「電話番号一致 かつ 座標が100m以内」など複合条件にすること。
- 統合時は、より情報量の多いレコードを優先し、失われる情報がないようマージする。

### 10-2. データ更新
同じ店舗を毎回新規登録しない。`(source, source_business_id)` でupsertする。
`last_checked_at` / `last_rating` / `last_review_count` / `last_website_status` を保存し、変化があれば `business_history` に記録する。

### 10-3. スコアのスナップショット（後付け検証のため必須）
`businesses.lead_score` を上書き更新するだけでは、「スコアが高い店は実際に成約したのか」を後から検証できない。
**リードを営業対象として確定した時点のスコアと、その内訳（各項目の点数）を `business_history` に必ずスナップショットとして残すこと。** これがないと §13 のビジネス指標が測定不能になる。

## 12. 検索の自動拡張と堅牢性

### 12-1. 「柏市を全件調査」モード
市内を複数地点・複数カテゴリに分割して検索し、重複排除する。
1リクエストの取得上限（DataForSEOは1,000件）を超える場合、まずページング（offset）を試し、それでも取りこぼす場合に地点・カテゴリ分割にフォールバックする。

### 12-2. レジューム可能にすること（重要・仕様の抜け漏れ）
全件調査は数十リクエストに及ぶ。途中でAPIエラーや予算上限で停止した場合、**最初からやり直すとコストが二重にかかる**。
- 調査ジョブを `search_jobs` テーブルで管理し、各サブクエリの完了状態を記録する
- 中断後は未完了のサブクエリからレジュームできるようにする
- 部分的に成功した結果は必ず保持する（全部捨てない）

### 12-3. エラーハンドリング
- APIエラー時：自動リトライ（exponential backoff、最大3回）→ エラー記録 → 部分的成功を保持
- Webサイトアクセス失敗時：「取得失敗」として処理し、店舗情報そのものは失わない
- 予算上限到達時：即座に停止し、その旨をUIに明示する

## 14. 開発の進め方（この順番で進めること）

**いきなり大規模システムを作らないこと。以下のステップごとに区切り、各ステップの完了時に必ず立ち止まって報告し、レビューを受けてから次に進むこと。**

### Step 0: 現状把握と設計確認（コードを書く前に）
1. 既存のスキャフォールド（`src/`, `supabase/`, `docs/ARCHITECTURE.md`）を読んで理解する
2. 以下を整理して**報告する**（実装はまだしない）：

3. 不明点・仕様の矛盾があれば、推測で進めずに質問する

### Step 1: DataForSEO 疎通確認（最優先）
- `scripts/test-dataforseo-search.mjs` を実行し、実レスポンス構造を確認する
- 確認結果に基づいて `DataForSEOProvider.ts` のパース部分を実データに合わせて確定する
- レスポンスの型を `zod` 等でバリデーションし、想定外のスキーマ変更を検知できるようにする
- **ここが確定するまで他の実装に進まないこと。** 全体の型がここに依存している。

### Step 2: Supabase構築 + 予算ガード
- `supabase/schema.sql` を適用（`api_usage`, `search_jobs` テーブルを追加）
- RLS を設定
- 予算ガード（`MONTHLY_BUDGET_USD` 超過で例外を投げる）を実装し、テストを書く
- **予算ガードは、外部API呼び出しを行う全モジュールが必ず通る場所に置くこと**（後付けで漏れると事故になる）

### Step 3: Phase 1 検索フロー（最小の縦切り）
- 検索条件 → DataForSEO呼び出し → フィルタ → 重複排除 → DB保存 → 一覧表示

- **ここまでで「柏市で条件に合う店舗リストが画面に出る」状態を作る。** 一度動かして確認する。

### Step 4: UI（検索画面 / 一覧 / 店舗詳細 / CSV出力）
- Step 3 の実データを見ながら作る

### Step 5: Phase 2（Web検索 → サイト解析 → メール抽出 → 完全なスコアリング）

### Step 6: AI営業分析（営業トーク / 提案生成）

### Step 7: CRM機能 / ビジネス指標ダッシュボード

### 開発時の共通ルール
- TypeScript は strict モード。`any` は原則禁止（外部APIレスポンスのパース直後のみ許容し、即座に型付きオブジェクトに変換する）
- スコアリング・判定ロジック・重複排除には**必ずユニットテストを書く**（Vitest）。ここのバグは静かにリストの質を下げるため
- 外部APIを叩くテストは、実際のレスポンスをfixtureとして保存し、それに対してテストする（テストで課金しない）
- コミットは機能単位で細かく分ける

## 16. 【判断が必要】ユーザーが決める必要がある事項

以下は元の仕様書に矛盾または未定義があるため、実装前に確認すること。

### 16-1. Phase 1 MVP のスコープが仕様書内で矛盾している
元の仕様では「Phase 1 = 店舗リスト・電話番号・CSVまで。メール/SNS/Web品質/Lead ScoreはPhase 2」とされている一方、「MVPの絶対条件」には SNS・メール探索・営業優先順位が含まれている。**両立しない。**

推奨：**Phase 1 は §14 Step 3 の範囲（店舗リスト + 簡易Lead Score + CSV）に絞る。** メール探索とAI営業分析はPhase 2へ。理由：メール探索は1店舗あたり数回のHTTPアクセスが必要で、最も時間とリスク（クロール規約）がかかる部分であり、ここでMVPを止めると全体が遅れる。

### 16-2. 利用者は1人か複数か
RLS設計とAuthの要否が変わる。個人利用ならAuthを省略してローカル実行でもよい。

### 16-3. 医療・士業など規制業種の扱い
HP制作営業自体は問題ないが、制作するHPの内容に広告規制がかかる業種がある（医療広告ガイドライン等）。
推奨：**スコアで下げるのではなく、店舗詳細に「この業種は広告規制の確認が必要」という注記を表示するだけにする。** 営業機会としては有望なため。
また、宗教法人・政治団体・公共機関は営業対象外として除外リストに入れることを推奨。

### 16-4. 検索プロバイダの選択
Google Custom Search JSON API と Brave Search API のどちらを使うか。実装前に両方の現在の無料枠を確認し、比較して報告すること。

## 18. 最後に

このプロジェクトで最も重要なのは以下の3点。迷ったらここに立ち返ること。

1. **2段階取得を崩さない** — Phase 1 を通過しない店舗にコストをかけない。これが低コストを成立させる唯一の仕組み。
2. **データを捏造しない** — 電話・メールの推測生成は禁止。AI推定値と実データを混ぜない。出所を必ず記録する。
3. **「店舗リスト」ではなく「営業マシン」を作る** — 件数ではなく、「電話をかける価値のある店が上位に来ているか」で品質を判断する。
